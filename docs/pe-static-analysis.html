What PE static analysis actually is

A Portable Executable (PE) is the file format Windows uses for .exe, .dll and .sys files. Static analysis means learning what one of these files is and what it can do by reading its bytes on disk, never by executing it. That distinction matters: running an unknown sample is how you get infected, so the ability to reach a confident opinion without detonation is the whole point.

The good news is that a PE file has to tell the operating system a lot about itself before Windows will load it — which functions it needs, how its memory is laid out, when it was built, who signed it. All of that is readable from the file, and a surprising amount of malicious intent leaks out of those structures. Static analysis is the discipline of reading them.

The six things to read first

You do not need a disassembler to form a strong first opinion. These six signals catch the majority of commodity malware in triage.

1. Hashes and fuzzy hashes

Start with identity. MD5, SHA-1 and SHA-256 uniquely name the file so you can look it up and share it. Then the interesting ones: an imphash fingerprints the import table so you can pivot to other samples in the same family, and fuzzy hashes like TLSH and ssdeep let you cluster files that are similar but not identical — exactly what you get from a malware builder churning out variants.

2. The PE headers

The headers carry cheap tells. The compile timestamp can be implausible (dated in the future, or years before the file appeared). The subsystem tells you console vs GUI. A rich header fingerprints the exact toolchain that built it, and a leftover PDB path in the debug directory sometimes hands you a developer username or project name — an attribution goldmine.

3. Sections and entropy

Each section declares a name, permissions and size. Two things jump out here. First, entropy: a value at or above roughly 7.2 (on a 0–8 scale) means the section is compressed, packed or encrypted — a classic way malware hides its payload. Second, permissions: a section that is both writable and executable (RWX) is rare in honest software and common in packers and shellcode loaders.

4. Imports and capabilities

The import table lists the Windows API functions the file calls. This is the richest single signal, but only if you read it correctly. Listing LoadLibrary proves nothing — half of Windows uses it. What matters is rare primitives and dangerous combinations: process-injection calls (VirtualAllocEx, WriteProcessMemory, CreateRemoteThread), input capture (SetWindowsHookEx), or the tell-tale pairing of encryption plus networking, which is the shape of both ransomware and command-and-control.

5. The digital signature

Do not stop at "a certificate is present." Verify it. Windows can check an Authenticode signature (embedded or catalog) and tell you whether it still validates. A file that carries a certificate that no longer verifies is a tampering or forgery signal — far more interesting than an unsigned file.

6. Embedded strings and indicators

Finally, sweep the file for readable strings and pull out embedded indicators of compromise: URLs, IP addresses, domains, registry paths, suspicious file names. A hard-coded IP in an otherwise plain utility is a lead worth pivoting on with threat intelligence.

Reading the result: what is actually suspicious

The mistake beginners make is treating a long import list as scary. It is not. Judgement comes from weighting the rare over the common, and from combinations. The table below is a rough sense of how much different findings should move your suspicion.

FindingOn its ownWhy
Uses LoadLibrary / CreateProcessIgnoreUbiquitous in benign software
High-entropy section (≥7.2)NotablePacked or encrypted payload
RWX sectionStrongRare in honest code; typical of loaders
Process-injection APIsStrongCore technique for stealth and evasion
Crypto + networking togetherStrongRansomware and C2 both look like this
Certificate present but invalidStrongTamper or forgery signal

None of these is a conviction on its own. A packer is used by plenty of legitimate commercial software; encryption is everywhere. The verdict comes from stacking weak-to-strong signals and cross-checking against threat-intel consensus — which is exactly why a scoring engine that understands combinations beats eyeballing a raw import dump.

Where static analysis stops

Be honest about the ceiling. Static analysis reads what the file declares; it cannot see what the file does at runtime. A heavily obfuscated sample that resolves its imports dynamically, decrypts its payload in memory, or pulls its real code from the network will look quiet on disk. Entropy heuristics partly compensate, but a low static score is a prompt to keep going, not a clean bill of health.

The professional workflow is layered: fast static triage first to sort the obvious and prioritise, then threat-intel enrichment, then — for anything that matters — dynamic analysis in a sandbox where you watch the real behaviour. Static analysis earns its keep at the front of that funnel, where speed and safety matter most.

FAQ

What is PE static analysis?

It is examining a Windows Portable Executable (.exe, .dll, .sys) by reading its bytes on disk rather than running it. You inspect the headers, sections, entropy, imported functions and digital signature to judge intent and risk without ever executing the sample.

Can you tell if an EXE is malware without running it?

Often, yes. Packed high-entropy sections, RWX memory, dangerous import combinations (encryption plus networking), a forged or missing Authenticode signature, and embedded URLs or IPs give strong evidence. Static analysis cannot see runtime behaviour, though, so a low score is not proof of safety — pair it with a sandbox detonation for anything important.

What is entropy in a PE file and why does it matter?

Entropy measures how random a section's bytes are, from 0 to 8. Normal code sits near 6. A section at 7.2 or above is usually compressed, packed or encrypted — a common way malware hides its real payload from static analysis.

What is an imphash?

An imphash is a hash of the PE import table in the order the functions appear. Because a given compiler and linker tend to produce the same import layout across builds of the same malware family, matching imphashes is a quick way to cluster related samples.
